# 04. 아키텍처 및 데이터 구조

## 전체 구조 (웹 버전 기준)

```
┌─────────────────────────────┐
│  브라우저 (127.0.0.1:5001)   │
│  index.html + app.js        │  ← 사용자가 보는 화면
└──────────┬──────────────────┘
           │ fetch (REST API) / SSE (실시간 로그)
┌──────────▼──────────────────┐
│  app.py — Flask 서버         │
│  ├─ REST API 라우트          │  설정/계정/대기열 CRUD, 파일 파싱, 로그인 트리거
│  ├─ scheduler_loop (스레드)  │  5초마다 queue.json 검사, 시간 되면 작업 발사
│  └─ log_queue → SSE 스트림  │
└──────────┬──────────────────┘
           │ ThreadsProUploader 호출 (작업당 새 스레드 + 새 이벤트루프)
┌──────────▼──────────────────┐
│  uploader.py                │
│  ├─ rewrite_content()       │  → OpenAI / Gemini API (본문 리라이팅)
│  ├─ ThreadsProUploader      │  → Playwright로 Chromium 조종
│  └─ ThreadsUploader (구버전) │  (main.py GUI 전용)
└──────────┬──────────────────┘
           │ Playwright (CDP)
┌──────────▼──────────────────┐
│  Chromium → threads.net     │  실제 게시가 일어나는 곳
└─────────────────────────────┘

파일 저장소 (DB 없음):
  config.json   설정 + 계정 목록 + API 키
  queue.json    예약 대기열 (작업 상태 포함)
  sessions/     계정별 로그인 쿠키(storage_state) + 크롬 프로필
```

## 게시물 하나가 올라가기까지의 흐름

1. **입력** — 사용자가 데이터 입력 탭에서 행 작성(또는 CSV 업로드 → `POST /api/upload_file`이 파싱해 표에 채움) → "예약 실행" → `POST /api/queue`로 전체 행이 `queue.json`에 저장되고 `POST /api/start`로 스케줄러 시작.
2. **감지** — `scheduler_loop`가 5초마다 현재 시각(HH:MM)과 `Pending` 행들의 `time`을 비교. 일치하면:
   - 같은 계정 작업이 실행 중인지 확인 (`running_accounts` 집합으로 중복 방지)
   - 행 상태를 `Running`으로 바꿔 저장
3. **전처리** (스케줄러 스레드에서):
   - `file` 값 파싱 → 폴더면 내부 미디어 파일 나열, macOS 한글 자소분리(NFC/NFD) 경로 보정, `Desktop/thread_ing` → `thread_ing` 경로 치환
   - AI 옵션이 GPT/Gemini면 `rewrite_content()`로 본문 리라이팅 (실패 시 원문 그대로 사용)
   - 태그·주제를 `#태그` 형식으로 본문 끝에 병합
4. **게시** (작업별 백그라운드 스레드에서 `post_to_threads()` 실행):
   1. 저장된 세션 파일로 Chromium 컨텍스트 생성, threads.net 접속
   2. 로그인 상태 검증 (로그인/로그아웃 상태 선택자 폴링)
   3. 워밍업: 피드 3~5회 사람처럼 스크롤
   4. "새로운 스레드" 버튼 클릭 (실패 시 단축키 `c` 시도) → 작성 모달 감지
   5. 본문 타이핑 → 미디어 첨부 (`input[type=file]` 직접 주입, 실패 시 FileChooser 방식) → 이미지 프리뷰 생성 대기(최대 10초)
   6. 댓글이 있으면 "스레드에 추가" 클릭 → 두 번째 입력칸에 댓글 타이핑 → 링크 미리보기 카드 제거
   7. "게시" 버튼 활성화 대기 → 클릭 (최대 3회 재시도) → 작성 모달이 닫히는지로 성공 판정
   8. 실패 시 `sessions/error_*.png` 스크린샷 저장
5. **기록** — 결과에 따라 행 상태를 `Success`/`Fail`로 바꿔 `queue.json` 저장, `running_accounts`에서 계정 제거.
6. **표시** — 모든 단계의 로그가 `log_queue`에 쌓이고 `GET /api/logs`(SSE)로 대시보드 콘솔에 실시간 표시. 프론트는 1.5초마다 `GET /api/status`와 `GET /api/queue`를 폴링해 상태 갱신.

## REST API 목록 (app.py)

| 메서드/경로 | 역할 |
|-------------|------|
| `GET /` | 웹 화면(index.html) 반환 |
| `GET/POST /api/config` | 설정 조회/저장 (headless, publish_delay, API 키, system_prompt) |
| `GET/POST/DELETE /api/accounts` | 계정 목록 조회(로그인 상태 포함)/추가/삭제 |
| `POST /api/accounts/rename` | 계정 닉네임 변경 (세션 파일·대기열·핸들 매핑까지 일괄 변경) |
| `POST /api/login` | 해당 계정의 수동 로그인 브라우저 창 띄우기 |
| `POST /api/ai/rewrite` | 본문 1건 AI 리라이팅 (표의 🔄 리롤 버튼용) |
| `POST /api/upload_file` | CSV/엑셀 업로드 → 행 목록(JSON)으로 파싱해 반환 |
| `GET/POST /api/queue` | 예약 대기열 조회/전체 교체 저장 |
| `GET /api/logs` | SSE 실시간 로그 스트림 |
| `POST /api/start` / `POST /api/stop` | 스케줄러 시작/중지 |
| `GET /api/status` | 스케줄러 실행 여부 |

## 데이터 파일 형식

### config.json

```json
{
  "headless": false,
  "publish_delay": 10,
  "openai_api_key": "sk-...",
  "gemini_api_key": "AIza...",
  "system_prompt": "친근한 말투로 다시 써줘...",
  "accounts": ["계정닉네임1", "계정닉네임2"],
  "account_handles": { "계정닉네임1": "actual_threads_handle" }
}
```

- `accounts`: 프로그램 내 관리용 닉네임 목록
- `account_handles`: 닉네임 → 실제 로그인된 Threads 핸들(@아이디). 로그인 성공 시 자동 기록
- ⚠️ API 키가 평문 저장됨. `.gitignore`에 포함되어 git에는 안 올라가지만 파일 자체는 보호되지 않음

### queue.json

행(게시물) 객체의 배열:

```json
[
  {
    "content": "본문 텍스트",
    "comment": "첫 댓글 (쿠팡 링크 등)",
    "file": "/path/to/img1.jpg, /path/to/folder",
    "tag": "#태그1, 태그2",
    "topic": "간식",
    "time": "09:00",
    "lang": "KO",
    "ai": "OFF",
    "account": "계정닉네임1",
    "status": "Pending"
  }
]
```

- `status`: `Pending` → `Running` → `Success` | `Fail`
- 프론트에서 "예약 실행"을 누를 때마다 **파일 전체가 통째로 교체**됨

### sessions/ 폴더

| 파일 | 내용 |
|------|------|
| `<safe닉네임>.json` | Playwright `storage_state` (쿠키 + localStorage). **로그인 세션 그 자체 — 민감 정보** |
| `profile_<safe닉네임>/` | 수동 로그인 시 사용하는 크롬 persistent 프로필 |
| `error_editor_*.png`, `error_post_*.png` | 게시 실패 시점의 화면 스크린샷 (디버깅용) |

`safe닉네임` = 닉네임에서 영문/숫자/`_`만 남긴 것 (`re.sub(r"[^a-zA-Z0-9_]", "", username)`).

## 동시성 모델 (왜 스레드가 이렇게 많은가)

- Flask 서버는 메인 스레드에서 HTTP 처리.
- `scheduler_loop`는 daemon 스레드 1개로 상시 회전 (5초 주기).
- 게시 작업 1건마다 새 daemon 스레드가 생기고, 그 안에서 **새 asyncio 이벤트 루프**를 만들어 Playwright(async)를 돌림. 이렇게 해야 한 작업이 몇 분 걸려도 스케줄러가 다른 계정의 다음 작업을 계속 감지할 수 있음.
- 같은 계정의 동시 게시는 `running_accounts` 집합 + 락으로 막음 (다른 계정끼리는 병렬 실행 가능).
- 로그는 스레드 어디서든 `log_queue.put()` → SSE 제너레이터가 꺼내서 브라우저로 push.

⚠️ 이 구조에서 `queue.json`을 여러 스레드가 각자 읽고 통째로 저장하기 때문에 **서로 덮어쓰는 경쟁 상태(race condition)** 가 존재합니다. 자세한 건 문서 06 참고.

## 구버전 GUI(main.py) 데이터 흐름 (참고)

웹 버전과 달리 시간 예약이 없고 **"엑셀 행 순서대로, N분 간격 순차 업로드"** 방식:

1. 엑셀에서 `폴더명`(번호), `본문`, `댓글` 열을 읽음
2. 작업 폴더에서 `1_일본양말`처럼 숫자로 시작하고 `[완료]`가 안 붙은 폴더를 번호순으로 찾음
3. 엑셀의 번호와 폴더를 매칭 → 폴더 안의 이미지(파일명 숫자순)와 `.txt`(본문 대체) 사용
4. 업로드 성공 시 폴더명 앞에 `[완료] `를 붙여 재실행 시 건너뜀
5. 설정한 간격(기본 30분)만큼 기다렸다가 다음 행 진행

`스레드 이미지/` 폴더가 바로 이 방식용 샘플 데이터입니다 (`1_일본양말`, `1_뉴욕쿠키`, `3_한성기업 만두`).
