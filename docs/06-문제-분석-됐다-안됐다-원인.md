# 06. 문제 분석 — 왜 됐다가 안 됐다가 하는가

이 문서는 코드를 실제로 읽고 **확인한** 버그와 구조적 한계를 정리한 것입니다.

> ✅ **2026-07-14 업데이트:** 아래 항목 중 코드로 고칠 수 있는 것들(A-4, B-1~B-9)은 모두 수정되어 저장소에 반영됐습니다. 각 항목의 원문 분석은 기록용으로 남겨두고, 수정 내용을 "✅ 수정됨" 표시로 덧붙였습니다. A-1~A-3(태생적 한계)은 코드 수정으로 없앨 수 없으므로 여전히 유효합니다.

"됐다 안 됐다"의 원인은 크게 세 층입니다:

1. **태생적 한계** — Threads 화면을 흉내 내는 브라우저 자동화라서 원래 깨지기 쉬움
2. **코드 버그** — 확인된 명백한 오류들
3. **설계상 함정** — 버그는 아니지만 특정 조건에서 조용히 실패하는 부분

---

## A. 태생적 한계 (고칠 수 없거나 계속 관리해야 하는 것)

### A-1. Threads UI 선택자 의존 ⭐ 가장 큰 원인

게시 과정 전체가 `aria-label="새로운 스레드"`, `div[role="button"]:text-is("게시")` 같은 **화면 요소 선택자**에 의존합니다 (`uploader.py` 곳곳). Meta가 Threads UI를 조금만 바꿔도(버튼 문구, HTML 구조, 클래스명) 해당 단계가 실패합니다.

- 한국어/영어 라벨만 하드코딩되어 있어 **계정 언어 설정이 다르면** 즉시 실패
- Meta는 사용자별로 UI를 점진 배포(A/B 테스트)하므로 **같은 코드가 계정에 따라, 날에 따라 되다 안 되다** 하는 것이 자연스러운 결과
- 대응 도구로 `dump_modal.py`(현재 버튼 HTML 덤프)가 있음 — 깨졌을 때 새 선택자를 찾는 용도

### A-2. 봇 감지

베지에 곡선 마우스, 워밍업 스크롤, webdriver 숨김 등 회피 장치가 있지만 완전하지 않습니다. Meta 측 감지 강도에 따라 로그인 세션이 무효화되거나 게시가 조용히 막힐 수 있고, **계정 제재 위험**도 있습니다. 특히 **Headless 모드는 감지가 더 쉬워** UI에도 "체크 해제 권장"이라고 적혀 있습니다. 안 될 때는 우선 headless를 끄세요.

### A-3. 세션 만료

로그인 쿠키(`sessions/*.json`)는 영원하지 않습니다. 만료되면 "로그인 세션이 만료되었거나 비활성 상태입니다" 로그와 함께 실패합니다. 계정 목록의 "로그인 완료" 표시는 **파일 존재 여부만 볼 뿐 쿠키가 살아있는지는 확인하지 않으므로**, 상태가 초록이어도 실제로는 만료됐을 수 있습니다. → 해결: 해당 계정 "로그인" 재수행.

### A-4. `networkidle` 대기 타임아웃

`post_to_threads`가 접속 직후 `page.wait_for_load_state("networkidle")`을 기다립니다. Threads 홈은 피드를 계속 불러와서 **네트워크가 조용해지는 순간이 안 올 때가 많고**, 그러면 30초 후 `PlaywrightTimeoutError` → "스레드 페이지 응답 속도 지연 초과" 실패. 네트워크 상태·피드 양에 따라 복불복이라 전형적인 "됐다 안 됐다" 패턴을 만듭니다.

✅ **수정됨:** networkidle 대기를 10초 제한 + try/except의 best-effort로 완화. 도달하지 못해도 그대로 진행합니다.

## B. 확인된 코드 버그

### B-1. 🔴 uploader.py에 `import pandas as pd` 누락 — GUI 버전 사망

`ThreadsUploader.load_excel_data()`와 `start_upload_process()`가 `pd.read_excel`, `pd.notna`를 쓰는데 파일 상단에 pandas import가 없었습니다. GUI(main.py)에서 "자동 업로드 시작"을 누르면 즉시 `NameError: name 'pd' is not defined`.

✅ **수정됨:** uploader.py 상단에 `import pandas as pd` 추가.

### B-2. 🔴 GUI 로그인 버튼 — 존재하지 않는 인자 전달

`ThreadsUploader.open_login_session()`이 `run_manual_login(self.username, headless=False)`를 호출했지만, `run_manual_login`의 시그니처는 `(self, username)`뿐입니다. GUI에서 "스레드 로그인 세션 열기"를 누르면 `TypeError`.

✅ **수정됨:** `headless=False` 인자 제거.

→ B-1, B-2 때문에 구버전 GUI는 한동안 어떤 경로로도 정상 동작이 불가능했습니다. 웹 버전(app.py)은 `ThreadsProUploader`만 쓰므로 이 두 버그의 영향이 없었습니다.

### B-3. 🔴 requirements.txt 불완전 — 새 환경에서 즉시 사망

`flask`, `openai`, `google-generativeai`가 코드에서 import되는데 requirements.txt에 없었습니다. 원래 개발 PC의 venv에는 수동 설치되어 있었겠지만, **다른 컴퓨터로 옮기거나 venv를 새로 만들면** `import openai`(uploader.py 상단)에서 바로 죽습니다. AI 기능을 안 써도 import 자체가 실패한다는 점이 함정입니다.

✅ **수정됨:** requirements.txt에 세 패키지 추가. 이제 `pip install -r requirements.txt` 하나로 충분합니다.

### B-4. 🟠 예약 시각을 놓치면 영영 실행 안 됨

`scheduler_loop`(app.py)의 시간 매칭이 `row["time"] == 현재 HH:MM` **정확 일치**였습니다. 그래서:

- 같은 계정의 앞 작업이 실행 중이라 건너뛴 경우, 로그는 "다음 주기(분)에 재시도"라고 하지만 실제로는 **그 분(minute) 안에서만** 재시도됨. 1분이 지나면 `time`이 현재 시각과 달라져 그 행은 **Pending인 채 영원히 방치** (게시 한 건이 보통 1~2분 걸리므로, 같은 계정 예약을 촘촘히 잡으면 반드시 발생)
- 예약 시각에 서버가 꺼져 있었거나 자동화가 정지 상태였어도 마찬가지로 소급 실행 없음

**증상:** 대시보드에 "대기" 상태로 계속 남아 있는 행.

✅ **수정됨:** 예약 시각이 도래한 뒤 **30분(`GRACE_MINUTES`) 이내면 실행**하도록 변경 (자정 넘김 고려). 같은 계정의 앞 작업에 밀린 예약도 앞 작업이 끝나는 대로 이어서 실행됩니다. 30분이 넘게 지난 예약은 여전히 실행하지 않는데, 이는 한참 지난 예약 수십 건이 한꺼번에 쏟아지는 사고를 막기 위한 의도적 제한입니다.

### B-5. 🟠 queue.json 동시 쓰기 경쟁 (race condition)

작업 스레드(`run_upload_task`)가 **작업 시작 시점의 대기열 스냅샷**을 들고 있다가 끝날 때 통째로 저장했습니다. 그 사이에:

- 사용자가 데이터 입력 탭에서 "예약 실행"으로 대기열을 수정하면 → 작업이 끝나는 순간 **옛날 스냅샷이 사용자의 수정을 덮어씀**
- 다른 분(minute)에 스케줄러가 저장한 상태 변경도 서로 덮어쓸 수 있음

**증상:** 분명히 고쳤는데 대기열이 옛날로 돌아가 있거나, 성공/실패 상태가 사라짐.

✅ **수정됨:** 전역 `queue_lock` 도입 + 상태 변경은 `update_row_status()`가 저장 직전에 파일을 다시 읽어 **해당 행(계정+시간+본문으로 식별)만 갱신**하도록 변경. API의 대기열 저장/조회도 같은 락을 사용합니다.

### B-6. 🟡 발행 후 대기 시간(publish_delay) 설정이 무용지물

설정 화면의 "발행 후 대기 시간(초)"은 `post_to_threads(..., publish_delay=10)`으로 전달되지만, **함수 본문 어디에서도 사용되지 않았습니다.** 게시 후 대기는 5초로 하드코딩.

✅ **수정됨:** 게시 성공 후 브라우저를 닫기 전 대기 시간으로 `publish_delay` 값을 사용 (잘못된 값이면 5초로 폴백).

### B-7. 🟡 한글 닉네임의 세션 파일명 충돌

세션 파일명은 닉네임에서 영문/숫자/`_`만 남겨 만들었습니다. 한글로만 된 닉네임은 **빈 문자열**이 되어 `.json` 하나로 뭉개지고, "본계정"/"부계정" 같은 두 계정이 **같은 세션 파일을 공유**하게 됩니다. → 다른 계정으로 로그인했는데 엉뚱한 계정으로 글이 올라가는 사고 가능.

✅ **수정됨:** 공용 함수 `safe_session_name()` 도입 (uploader.py에 정의, app.py도 동일 함수 사용). 영문/숫자/`_`로만 된 닉네임은 기존 파일명 그대로, 그 외 문자가 섞인 닉네임은 닉네임 MD5 해시 8자리를 덧붙여 충돌을 방지합니다 (예: `본계정` → `u_63171d31.json`, `내계정1` → `1_991d8345.json`). **주의: 수정 전에 한글 섞인 닉네임으로 로그인해 둔 계정은 파일명 규칙이 바뀌므로 재로그인이 한 번 필요합니다.**

### B-8. 🟡 클라이언트 로그가 화면에 안 보임

`static/app.js`의 `appendClientLog()`가 `<div>`인 콘솔 박스에 `consoleBox.value += ...`를 사용 — div에는 value 속성이 없어 아무것도 표시되지 않았습니다. CSV 파싱 결과, AI 일괄 변환 진행 상황 같은 안내가 조용히 사라졌습니다 (동작 자체는 정상, 로그만 안 보임).

✅ **수정됨:** SSE 핸들러와 같은 `appendChild` 방식으로 변경.

### B-9. 🟡 영상(mp4) 첨부 시 업로드 완료 판정 부정확

미디어 업로드 완료를 "모달 안 `<img>` 개수가 파일 수만큼 늘었는지"로 판정했습니다. 영상은 img 태그가 안 생길 수 있어 10초를 헛되이 기다린 뒤 "프리뷰가 생성되지 않았습니다" 경고와 함께 진행합니다. 큰 영상은 실제 업로드가 끝나기 전에 게시 버튼을 눌러 **미디어 없이 올라가거나 실패**할 수 있습니다.

✅ **수정됨:** `img`와 `video` 요소를 함께 세도록 변경. (아주 큰 영상 파일은 여전히 10초 안에 프리뷰가 안 생길 수 있음 — 그 경우 경고 로그를 확인하세요.)

### B-10. 🟡 GUI와 웹의 세션 저장 위치가 달라 호환 안 됨

웹 버전은 `sessions/`, GUI 버전은 `threads_session/threads_session_<계정>/`을 사용합니다. 한쪽에서 로그인해도 다른 쪽에서는 "세션 없음"으로 나옵니다. 버그라기보다 두 버전이 분리된 흔적이지만, 사용자를 헷갈리게 하는 지점.

## D. "안 될 때" 진단 순서 (체크리스트)

1. **대시보드 SysTek Logs를 본다.** 모든 실패는 로그에 이유가 찍힌다.
2. `ModuleNotFoundError` → 구버전 requirements.txt로 만든 환경. `pip install -r requirements.txt` 재실행 (B-3)
3. "로그인 세션이 만료" → 해당 계정 재로그인 (A-3)
4. "응답 속도 지연 초과" → 네트워크 문제 또는 Threads 접속 자체가 느림. 재시도 (수정 전 버전이라면 A-4)
5. "작성 창을 열지 못했습니다" / "게시 버튼을 찾지 못했습니다" → Threads UI 변경 (A-1). headless를 끄고 눈으로 확인, `dump_modal.py`로 새 선택자 탐색
6. 행이 "대기"인 채 시간이 지나버림 → 예약 시각에서 30분이 넘게 경과 (B-4의 유예 한도). 시간을 다시 잡고 재실행
7. 계정 상태가 "로그인 완료"인데 "세션이 없습니다" 실패 → 한글 닉네임의 세션 파일명 규칙 변경 (B-7). 해당 계정 재로그인
8. 사진/영상이 빠진 채 올라감 → 파일 경로 확인(절대경로, 존재 여부), C-1, B-9
9. `sessions/error_*.png` 스크린샷을 열어 실패 순간의 화면을 확인
